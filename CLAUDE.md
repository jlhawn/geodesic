# Working in this repository

WebGCM: a browser climate model (JavaScript; CPU and WebGPU engines under `js/`), its page (`climate.html`, `js/climate.module.js`, `js/model.worker.js`), the explainer series under `explain/`, spin-up and analysis scripts under `scripts/`, tests under `test/` (`node --test`).

## Tools and tokens

- Put several steps in one Bash call; one command per turn is the expensive habit. Never poll in a loop of separate calls: use one `until … ; do sleep 20; done`, or run the job in the background and read its log once.
- Keep tool output short: `head`, `tail`, `grep`, `wc`, `cut -c1-200`. Send long output to a file and read the part you need. Read large files in ranges (`sed -n a,bp`, or Read with offset and limit); `docs/c-grid-dynamical-core.md` is 13,000 lines and `js/gpu/physics.gpu.js` 2,600.
- Do not `cat` binary files or state files (`runs/*.bin`, `data/*.bin`, `explain/data/*.bin`); read them through the modules that decode them.
- Report with file paths and a few lines, not pasted dumps. Finish in under about 80 tool calls; if the job needs more, stop and report what remains and why.

## The GPU

- Run node with Node 22 or newer (`.nvmrc`; on this Mac `~/.nvm/versions/node/v22.22.2/bin/node` when the shell picks v18): Node 18 has no `process.getBuiltinModule`, so the state-grid and geography loaders read no files and the sub-grid orography, and with it the form drag, is silently missing from every script run. `js/gpu/device.module.js` refuses to start on it.
- One GPU model at a time on this Mac: macOS aborts command buffers under contention, silently. Queue every GPU job (a test file that steps a GPU model, `scripts/spinup.mjs`, `oceanSpinup.mjs`, `explainOcean.mjs`, `fixedSst.mjs`, a profile) through the lock every session shares: `source scripts/gpuQueue.zsh` and `export GPU_WHO=<your session's name>` once, then `GPU_JOB='N=128 page check' gpu_run LOG cmd…` waits its turn in arrival order within its `GPU_PRIORITY` level (1, the highest: a check Joshua is waiting on; 2: test suites before a merge or push; 3: the default; 4: routine reports and figures; 5: long background experiments, in short segments), holds the GPU for the whole command, appends its output to LOG between `start` and `exit RC` lines and then the count of command-buffer aborts, and returns its status; a LOG that already holds `exit 0` is skipped. Wrap a multi-segment driver (`scripts/pairedSpinup.sh`, `asyncSpinup.sh`) in one `gpu_run`, never each segment, except a level-5 background experiment, which queues each segment so that other work runs between segments. CPU-only jobs run directly, outside the queue. `~/.cache/webgcm-gpu-queue/status.md` lists who holds the GPU and who waits, in order, each with its `GPU_JOB` line, and is rewritten on every change; `gpu_status` prints it. The queue also waits for GPU users outside it and for a page server on port 8000.
- WGSL that Apple's M5 Metal compiler gets wrong (Oct 2026; both engines agree on the M1, Safari and the CPU): (1) a loop that counts down over a thread-private array of more than 32 floats returns the array's zero initializer once Tint's robustness clamps are on and the bounds fold to constants after inlining; write such read-back loops counting up over the same indices. (2) A thread-private array that has been passed by pointer (`ptr<function, array<…>>`) to a function reads back as zeros in the caller's later loop; read the values from the buffer the array was filled from, or pass a copy. Neither shows at N = 8: before pushing kernel changes, run `test/boundaryLayer.test.mjs`, `test/gpuModel.test.mjs` and a CPU/GPU field comparison at the page's configuration (the probes, reports and the M1's results are on branch `m5-probe`). On the M1 too (Oct 17, the hybrid ocean's column kernels, N = 8): a function whose arrays live in module-scope `var<private>` storage is handed them by pointer and its second call in a thread keeps every third element of its first, and a loop that reads the array element it wrote in the previous iteration (a tridiagonal back substitution) loses every third element; keep column arrays local to the entry point, generate the routines inline, and carry a loop's previous element in a scalar.
- Timings taken under contention are worthless; alternate base and candidate runs and repeat them. The page loop on the M1 Max is already about 96 percent GPU-busy.
- Queue GPU test files one per `gpu_run` (one `node --test` runs its files concurrently); run CPU test files together as concurrent runners.

## Conventions

- Never commit `socol.txt`, anything under `runs/` beyond the page's default state parts, or scratch files.
- American spelling in prose, UI text, messages and comments. Code comments default to none and never narrate a change.
- The static server on http://localhost:8001 serves the repo root; do not start another, and do not open a GUI browser from an agent.
- No test builds or runs anything below N = 16, the coarsest grid the model runs at (its step is 1350 s, 64 a day).
- Both engines must stay in step: a model change lands on the CPU (f64) and the WGSL (f32) together, with a parity test at N = 16 and, where it touches storage or transport, a row in `test/layeredConservation.test.mjs` or `test/atmosphereConservation.test.mjs`.
- Saved states record their grid (`grid: { relax }`); loaders use `js/stateGrid.module.js`.
